Owner: Maximum-mini-NUIAK. Date: 2026-10-18.

## Milestone

Turn important research questions into repeatable, bounded experiment graphs with complete decision reports.
Use the existing queue, templates, catalog, and dashboard. Do not build another scheduler.
Tasks.md owns implementation status. This document owns the process and acceptance contract.
This plan does not grant capture, training, export, installation, promotion, or scheduling authority.

## Research priorities

| Goal | Practical outcome | Required measures | Next useful question |
|---|---|---|---|
| Standard control detection | Find usable native control boxes | Class-free recall, class errors, localization, regional and family support | Which missed controls need annotations, data, or detector correction? |
| Standard focus | Select focus or abstain correctly | End-to-end gains, lost successes, wrong selections, misses, no-focus decisions | Does a correction help with deployable boxes? |
| TTR delivery | Use qualified models through the real consumer | Preprocessing parity, identity, latency, package size, observer results | Does offline improvement survive the consumer path? |
| Optional HCF | Measure added value under verified OS HCF | Rules, crop, and detector results by profile and control family | Does HCF add useful coverage without weakening Standard? |
| Workflow efficiency | Reach usable decisions with less preparation | Preparation time, interventions, avoidable idle time, repeated bytes, useful decision cost | Which repeated manual step should become a tested adapter? |

Standard detection and focus control priority. HCF is not a prerequisite for Standard research.
Do not add incompatible metrics into one accuracy score. Known-box success is not full-screen detection accuracy.
Preserve no-focus, transition, localization, classification, and settling results as separate measurements.

## One repeatable iteration

1. Select a delivery goal and its largest measured gap.
2. Reuse completed evidence before proposing execution.
3. Define one campaign question, matched controls, and the decision that changes the next action.
4. Freeze membership, data roles, settings, initialization, thresholds, budgets, and approved branches.
5. Compile through supported templates. Check inputs, authority, resources, and producer dependencies.
6. Approve exact jobs. Let the detached runner execute them.
7. Publish a combined decision report with cases, support, gains, regressions, and evidence limits.
8. Close answered questions. Prepare the next approved branch or record its exact missing requirement.

Review the broader priorities at every campaign boundary. Do not let one narrow failure consume every subsequent iteration.
Each iteration includes a useful stopping point. It does not start an unlimited research loop.
Periodic chat reviews require separate explicit scheduling consent.

## Bounded selection rules

| Observation | Permitted next action | Stop condition |
|---|---|---|
| Missing focused-control proposals | Inspect coverage and identify eligible annotation or producer work | Missing labels or authority blocks only that branch |
| Usable proposals with failed selection | Run an approved geometry or competing-score diagnosis | No compatible inputs means an exact preparation requirement |
| Existing correction with compatible inputs | Run matched scoring before new training | Any retained regression prevents replacement |
| Useful gain with insufficient support | Run a predefined independent comparison or seed, if approved | Campaign budget or fixed evidence limit ends expansion |
| No useful gain after defined comparisons | Close volume expansion and diagnose the failed assumption | Do not repeat unchanged training |
| Invalid or incomplete evidence | Publish an invalid-evidence result | Never interpret missing evidence as model acceptance |

Parent models, variations, and selection rules remain pinned. Keep rejected candidates and their useful evidence.
Automatic selection means choosing among approved branches, not inventing unlimited mutations or changing release gates.
Freeze candidates before final audit. Do not repeatedly tune against reserved audit groups.

## Readiness and reserve

Prepare priority work, independent reserve work, and conditional follow-ups together.
These are execution lanes, not mandatory HCF, iOS, and tvOS quotas.
Target 25 useful ready jobs and 24–48 hours of estimated work when qualified inputs support them.
Refill below 10 useful ready jobs. Keep execution cycles at 5–10 jobs.
Report measured duration separately from diagnostic ceilings. Use unavailable when comparable timing evidence does not exist.
Report unmet capacity honestly. Do not add arbitrary sweeps, duplicate runs, or unnecessary long jobs.

Distinguish blocked prerequisites, normal dependency waits, exhausted budgets, rejected candidates, and superseded attempts.
An exhausted run needs useful checkpoint state, a justified continuation, and a remaining approved budget.
A blocked run needs a repair or producer. More time alone does not repair missing inputs.
Create a bounded producer task when a known capability can supply the missing input.
If no supported adapter exists, record one reusable implementation task with acceptance checks.

## Efficient execution without weaker evidence

Share verified preparation and cached predictions by complete input identity.
Preserve each arm's settings and report. Grouping jobs does not prove shared worker state or faster execution.
Measure setup, decoding, inference, training, transfer, and review separately when existing receipts support them.
Benchmark shared setup against separate setup before enabling it. Test order independence and state reset.
Use verified USB storage for authorized bulk outputs. Preserve source captures, labels, checkpoints, and useful failures.
Do not prioritize full backups of reproducible caches. Preserve restoration paths for important artifacts.
Reporting failure must not stop independent experiment execution.

### Implemented scope

`research_campaign451.py` accepts one bounded request and compiles a finite graph using the existing queue.
It creates diagnosis, matched comparison, and terminal report jobs.
It can place an existing-template T57 scoring description after diagnosis or reuse registered scoring jobs.
The comparison verifies unchanged frames, original groups, detector boxes, baseline scores, and fixed thresholds.
Scoring inputs must be available during compilation. Future scoring receipts remain verified dependencies.
The terminal report lists case outcomes, profile slices, diagnoses, retained failures, and the next requirement.
Known Standard regressions prevent a supported outcome. No report grants promotion.

This version sequences diagnosis and comparison. It does not invent a correction or perform automatic training selection.
Missing or invalid receipts block affected dependents. The runner preserves failure evidence and does not retry automatically.
The compiler bounds total new jobs, maximum execution seconds, and output bytes before admission.
These are conservative sums of per-job limits, not promised durations or a dynamic resource reservation service.
