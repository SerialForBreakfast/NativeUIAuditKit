## Follow-on implementation assignments (proposals, no capture authority)

### VIS-A — Truthful state and configuration provenance

Enabled/selected software subpacket DATA-STATE-01 is documented in
[its handoff](../../reports/work/DATA-STATE-01/handoff.md). It adds opt-in v1.2 without
migrating existing corpus/writer defaults. Native qualification and the broader
effective-theme/runtime provenance work below remain distinct outstanding scope.

Inputs: CaptureTypes.AnnotatedElement, AnnotationWriter, native renderer state,
GeneratorRunConfig and source/schema version policy. Keep existing public library
API unchanged. First specify optional unavailable state versus actual false; preserve
old sidecar decoding and declare any schema change before code. Carry true native
enabled/selected state where available; do not fabricate historical values. Audit
Chrome's template-specific colorScheme versus recorded run colorScheme before claiming
theme fidelity. Record requested config separately from observed runtime and effective
render configuration where different. Test real writer/capture boundaries using
enabled/disabled and selected/unselected fixtures, omitted/unknown values, roundtrip,
clipping and legacy decoding. Acceptance: no default presented as measured ground
truth, actual callers wired, focused tests and required offline package checks.
Native rendering qualification remains separately authorized.

### VIS-B — Independent visual schedule, bounded native probes

**DATA-SCHEDULE-01 implementation scope:** a planning-only generator command builds
48 configurations per representative family (UIKitControls,ChromeCoverage,DynamicTypeOverflow),
144 planned configurations total. No command executes these rows. Each future capture
batch is capped at48; the first qualification batch must select reviewed representatives
across families, not dispatch the entire catalog. All membership is development-only.
Required intersections are explicit: theme×profile,theme×type,clock×charge,
cellular×Wi-Fi,charge×charging-state, not all possible pairs of all dimensions.
Requested theme/config are planning inputs, not claims of effective rendering. Current
Chrome template's seeded theme and run theme can differ; qualification must resolve that
before admitting theme-specific evidence. Existing frozen loops remain untouched.
[Planning implementation and verified catalog](../../reports/work/DATA-SCHEDULE-01/handoff.md)
are available; this does not complete native probe qualification or a capture adapter.

Inputs: accepted VIS-A semantics and a newly versioned addon catalog, never the frozen
P0-C catalog. Build deterministic pairwise schedules with named axis streams; do not
reuse index parity for both theme and profile or text size. Explicitly test both themes
at both scales and each supported text size under each theme. Keep semantic constraints
(valid charging levels/locales) in the catalog. Stable recipe-family/parent groups own
all variants and their split; balancing cannot move captured members between splits.

Offline planning tests prove determinism, required pair coverage, allowed combinations,
group isolation and bounded catalog size. Separately authorized rendering starts with
at most48 cases across representative controls/chrome/long-text templates, fixed
content per contrastive probe. Verify decoded pixels AND annotation agreement; retain
unexpectedly identical or clipped results rather than counting metadata as success.
Probe both charging states at the same level and clock. Use actual runtime attribution.
Acceptance: coverage report identifies implemented/unsupported axes and every missing
cell, with no full-corpus recapture or Cartesian-product expansion.

### VIS-C — Targeted incremental data, not automatic retraining

**DATA-PROBE-01 software scope:** opt-in bounded native test adapter, canonical
catalog validation and Chrome effective-theme override. Catalog v2 fixes the
DynamicTypeOverflow request to accessibilityExtraExtraExtraLarge, matching source;
its theme/type diversity is explicitly unsupported. Preserve catalog v1 evidence
as planning-only and reject it for execution. Native execution requires explicit
target, catalog hash, selected IDs and a new output name. No legacy dataset loop
is entered. Default renderer and frozen reconstruction behavior remain unchanged.

Inputs: successful native probes and reviewed class/family gaps. Prioritize controls,
geometry, theme/type interactions and hard negatives before additional decorative
clock variants. Freeze new source groups and quotas before capture; preserve original
membership and evaluation exclusions. Version the addon and merged manifests, audit
all labels, lineage and duplicates, and report exact support by split. Training requires
one separately logged/approved experiment comparing identical untouched evaluation
membership. No accuracy improvement may be inferred from coverage counts alone.

## Verification scope

### DATA-PROBE-INTAKE — offline export admission

Finish the probe adapter's read-only consumer without launching capture. Require
an independently supplied catalog, selected IDs and exact target, not only the
batch's own assertions. Validate v1 receipt and strict v1.2 sidecars, all hashes,
PNG decode/dimensions, requested config and coordinate agreement. Reject partial,
unexpected membership, symlinks/traversal, duplicate JSON keys and false training
eligibility. Bound files/counts/pixels. Reuse existing schema validation.

Report requested coverage and decoded-pixel duplicates without silently deleting
examples. Successful integrity remains development-only, pending visual review;
runtime OS is producer-reported and requested traits are not verified rendering.
Test the real CLI against positive/adversarial local fixtures. No new cropper,
native execution, model inference, training or shared-status update is included.

Consumer command (after separately authorized capture/export into the project):
`PYTHONDONTWRITEBYTECODE=1 .venv-yolo/bin/python scripts/validate_visual_probe.py
--batch PROJECT_LOCAL_BATCH --catalog REVIEWED_CATALOG --case-id REVIEWED_ID
--target EXACT_SIMULATOR_UUID`. Repeat --case-id in original selection order.
Use the independently retained catalog, not the batch's own catalog as its expected
reference. Exit0 means integrity passed only; capture.json remains pending visual
review and no training permission is generated. Preserve stdout/stderr in a new
report location. No failed batch is overwritten or repaired by this tool.

This inventory uses read-only source/metadata analysis plus retained render evidence;
it makes no new model or runtime claim. Worker/model guidance separates rendering
proof, label truth, eligibility and accuracy. No shared-status update is needed for
the local iOS inventory; existing cross-project Photos request is unchanged.
