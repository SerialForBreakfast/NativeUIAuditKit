### VIS-B — Independent visual schedule, bounded native probes

**DATA-SCHEDULE-01 implementation scope:** a planning-only generator command builds
48 configurations per representative family (UIKitControls,ChromeCoverage,DynamicTypeOverflow),
144 planned configurations total. No command executes these rows. Each future capture
batch is capped at48; the first qualification batch must select reviewed representatives
across families, not dispatch the entire catalog. All membership is development-only.
Required intersections are explicit: theme×profile,theme×type,clock×charge,
cellular×Wi-Fi,charge×charging-state, not all possible pairs of all dimensions.
Requested theme/config are planning inputs, not claims of effective rendering. Current
Chrome template's seeded theme and run theme can differ; qualification must resolve that
before admitting theme-specific evidence. Existing frozen loops remain untouched.
[Planning implementation and verified catalog](../../reports/work/DATA-SCHEDULE-01/handoff.md)
are available; this does not complete native probe qualification or a capture adapter.

Inputs: accepted VIS-A semantics and a newly versioned addon catalog, never the frozen
P0-C catalog. Build deterministic pairwise schedules with named axis streams; do not
reuse index parity for both theme and profile or text size. Explicitly test both themes
at both scales and each supported text size under each theme. Keep semantic constraints
(valid charging levels/locales) in the catalog. Stable recipe-family/parent groups own
all variants and their split; balancing cannot move captured members between splits.

Offline planning tests prove determinism, required pair coverage, allowed combinations,
group isolation and bounded catalog size. Separately authorized rendering starts with
at most48 cases across representative controls/chrome/long-text templates, fixed
content per contrastive probe. Verify decoded pixels AND annotation agreement; retain
unexpectedly identical or clipped results rather than counting metadata as success.
Probe both charging states at the same level and clock. Use actual runtime attribution.
Acceptance: coverage report identifies implemented/unsupported axes and every missing
cell, with no full-corpus recapture or Cartesian-product expansion.
